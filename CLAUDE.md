# Tax Strategy Planner — project context for Claude Code

Read this before making changes. It is the project context Claude Code loads
automatically at the start of every session in this folder.

## What this is

A client-side tax planning tool for a CPA firm: enter a client's return data,
select tax strategies from a 109-item library, and compare Baseline vs.
Scenario 2 vs. Scenario 3 with a multi-year projection. Outputs: an advisor
technical view, a client-facing PDF report, a client slideshow, and an
anonymized pre-engagement pitch deck.

## Hard constraints — do not violate these

- **No build step, vanilla ES5 JavaScript.** No bundler, no transpiler, no
  package.json driving the app itself. Plain `<script>` tags, `var`,
  `function` (no arrow functions, no `let`/`const`, no template literals,
  no classes). The app must keep working opened directly as
  `file:///.../index.html` — this is the primary documented launch mode
  (see `Launch Tax Strategy Planner.cmd`), which rules out ES modules
  (`type="module"` is blocked by CORS under `file://`) and anything that
  needs a dev server. `scripts/*.js` (the Node-run validator/test/build
  tooling) are the only exception — those run under Node, not the browser.
- **Accuracy over speed.** This produces real numbers a CPA relies on.
  Never invent a dollar figure, IRC citation, or case name you are not
  highly confident is correct — an omitted authority is fine, a fabricated
  one is not. When in doubt, verify (web search, IRS Rev. Proc.) rather
  than guess, especially for anything version-pinned to a specific tax year.
- **One strategy per file, do not hand-edit the generated index.** See
  "Adding a strategy" below — `js/data/strategies-index.js` is generated,
  never edit it directly.

## Architecture

```
js/data/tax-tables-2026.js        constants ONLY — brackets, thresholds,
                                   limits, TSIQ.esc, TSIQ.fmt. The engine
                                   reads tax numbers from here and nowhere
                                   else. No tax constants live anywhere but
                                   this file.
js/data/strategies/<id>.js        one file per strategy (109 files); each
                                   pushes itself onto TSIQ.strategyModules.
js/data/strategies-index.js       GENERATED by scripts/build-index.js — a
                                   marker-delimited <script> block in
                                   index.html plus a line finalizing
                                   TSIQ.STRATEGIES = TSIQ.strategyModules.
                                   Never hand-edit; never insert a strategy
                                   <script> tag after this point in
                                   index.html (see checkStrategySnapshotDrift
                                   in app.js — it warns at load time if the
                                   two arrays' lengths ever disagree).
js/engine/tax-engine.js           TSIQ.computeYear(profile, state) — pure
                                   single-year tax computation.
js/engine/scenario-engine.js      TSIQ.computeScenario(profile, selections,
                                   years, growthRate) — runs a multi-year
                                   projection, applying each selected
                                   strategy's apply() in applyOrder, then
                                   computeYear() per year. Also
                                   TSIQ.bestScenario / TSIQ.incrementalSavings
                                   (shared by every renderer — don't
                                   reimplement "which scenario is best"
                                   locally in a renderer).
js/engine/suggest.js              TSIQ.suggestStrategies(profile) — runs
                                   every strategy's optional suggest(profile)
                                   rule-of-thumb screen.
js/engine/return-parser.js        client-side PDF text-layer parser for
                                   Import Return (PDF). See its own
                                   isEvalSupported:false comment before
                                   touching pdf.js version pinning.
js/renderers/common.js            shared helpers used by all 4 renderers:
                                   TSIQ.render.openWindow (popup + print),
                                   TSIQ.DEFAULT_BRAND_COLOR, TSIQ.APP_VERSION.
                                   Loads before the other renderer files.
js/renderers/advisor.js           in-app library card detail / strategy
                                   handout HTML.
js/renderers/client-report.js     print-to-PDF client report.
js/renderers/slideshow.js         client-facing full-screen deck. Also
                                   exports the shared dark "deck shell"
                                   (openDeck/deckLogo) the pitch deck reuses.
js/renderers/pitch-deck.js        anonymized pre-engagement sales deck.
js/app.js                         everything else: form I/O, scenario
                                   builders, results rendering, PDF import,
                                   client-file import/export, brand
                                   settings, session autosave.
```

Load order matters and is fixed in `index.html`: tax-tables-2026.js → all
109 strategy files → strategies-index.js → tax-engine.js →
scenario-engine.js → suggest.js → return-parser.js → renderers/common.js →
the other renderers → app.js.

## Table provenance

`js/data/tax-tables-2026.js` is federal 2026 law per Rev. Proc. 2025-32, as
amended by the One Big Beautiful Bill Act (OBBBA, P.L. 119-21, July 2025).
Every constant should be traceable to one of those two sources — when you
add or change a number, add a one-line comment saying where it came from
(see the existing entries for the expected style). When Rev. Proc. 2026-XX
(or later) drops for the next tax year: update `taxYear`, every bracket/
threshold/limit table, and re-run `node scripts/test-engine.js` — the
golden-file assertions are hand-derived against 2026 figures and WILL fail
in informative ways in they no longer match after an update (that's the
point: confirm each failure is the expected consequence of the table
change, not a formula bug, before updating the fixture's expected value).

## Adding a strategy

1. Copy any existing file in `js/data/strategies/` as a template — read
   `docs/strategy-authoring-spec.md` fully first.
2. Fill in `advisor`, `client`, `inputs`, `appliesTo`, `apply()`.
3. Run `node scripts/build-index.js` (regenerates the index.html script
   block + `TSIQ.STRATEGIES` finalizer), then
   `node scripts/validate-strategies.js` (schema + smoke-test every
   strategy across 5 synthetic profiles) and `node scripts/test-engine.js`
   (the golden-file engine suite — should still be 100% green; a new
   strategy shouldn't change any existing fixture's expected value).

The library cards, both scenario checkboxes, the PDF, the slideshow, and
the pitch deck all pick up a new strategy automatically — nothing else
needs to change.

## Testing

- `node scripts/test-engine.js` — hand-derived golden-file assertions
  against the tax engine and multi-year strategy stacking. Run after ANY
  change to `js/engine/*.js`, `js/data/tax-tables-2026.js`, or a strategy's
  `apply()` math.
- `node scripts/validate-strategies.js` — schema validation (required
  fields, `inputs[]` shape, `conflictsWith`/`requiresOneOf` id references
  and reciprocity) plus a smoke test that runs every strategy's `apply()`
  and `suggest()` against 5 synthetic client profiles (rich MFJ,
  W-2-only single, a loss year, high-income SSTB, and a retired MFJ couple
  on Social Security plus IRA/pension income) at 1x and 10x its default
  param values, checking for `NaN`/negative/thrown results.
- `node scripts/test-authority.js` — 110 assertions cross-checking the engine
  against the governing IRS worksheets rather than against itself: the §86
  Social Security Benefits Worksheet (both tiers and the 85%-of-gross
  ceiling), Schedule D Part III netting plus the Qualified Dividends and
  Capital Gain Tax Worksheet (including a short-term loss against a long-term
  gain, and preferential income spanning all three bands), Form 8995-A Part
  III (non-SSTB inside and above the phase-in range, and the SSTB
  double-reduction path), and Schedule SE / Form 8959 / Form 8960 together.
  Every expected value was derived from the worksheet BEFORE looking at engine
  output, then independently re-derived by a second pass trying to prove the
  first wrong. This is what found the senior-deduction bug. Read the header
  comment before adding to it — in particular, dollar thresholds come from the
  2026 tables while worksheet STRUCTURE comes from the IRS document, and each
  fixture records which of its inputs are statutory (survive a table refresh)
  and which are indexed (need re-deriving).
- `node scripts/test-invariants.js` — 48 assertions asking a different question
  from the other suites: can the tool promise a client more than the law
  allows? Scoped to strategies that share a statutory limit or the same
  dollars (§415(c) annual additions, §179, the LTCG pool, the depreciation
  tracker), plus a positive control on the general-business-credit family.
  Read the header before adding to it: "combined savings must not exceed the
  sum of the individual savings" is NOT a valid general rule, because
  strategies legitimately compound (an S-corp election creates entityW2Wages
  and unlocks the §199A wage prong). Savings comparisons run on a linearized
  profile so progressivity is the only nonlinearity left.
  Carries a `KNOWN_DEFECTS` registry for real defects awaiting a
  licensed-review call (see `FINDINGS-2B.md`). The suite exits 0 only when the
  failure set is EXACTLY that registry: a new break fails the run, and a known
  defect that starts passing ALSO fails the run so the registry cannot rot.
  Every known defect prints on every run; nothing is suppressed.
- `node scripts/test-renderers.js` — 48 assertions that the four renderers
  agree with each other and with the engine on the headline figures, that
  per-strategy incrementals use the scenario's own (possibly overridden)
  profile, that no renderer emits `$NaN`, and that the ET7 exact-vs-rounded
  split holds. Runs headless by stubbing `openWindow`/`openDeck`.
- `node scripts/ui-smoke.js` — 41-check browser sweep of the UI surface:
  every Section 1 field and checkbox, both tab panes, library search and
  the card detail modal, Suggest, strategy selection with its parameter
  block, Run Comparison, Solve, Copy Scenario 2 → 3, Undo, all three Brand
  Settings paths, all four popup renderers, export/import round trip, and
  an all-zero edge profile. Three of the checks are numeric rather than
  structural: they re-run `TSIQ.computeScenario` in the page and assert the
  KPI tiles tie to it. Passing requires zero console errors in the app AND
  in every popup it opens. Optional, not part of the required loop — it
  needs Playwright, which the app itself does not depend on:
  `npm i -D playwright && npx playwright install chromium`. Set
  `SMOKE_OUT=<dir>` to keep the screenshots it captures. It is a smoke
  sweep, not exhaustive: it exercises 2 of the 109 strategies through the
  UI, since `validate-strategies.js` already runs all 109 `apply()`
  functions against 5 profiles and the browser adds nothing there.
- Anything the smoke sweep does not cover still needs a look by hand in a
  browser. Two traps when scripting the UI, both of which cost a debugging
  round before `ui-smoke.js` accounted for them: KPI values animate via
  `requestAnimationFrame` on render (`animateResults()` in app.js), so a
  check that reads `.textContent` immediately after clicking Compute
  catches a mid-animation frame, not the final value — wait ~800ms, set
  `prefers-reduced-motion: reduce`, or read the `data-target` attribute
  instead. And every strategy checkbox sits inside a collapsed `<details>`,
  which a driver will refuse to click; open them first.
- `TSIQ.__test` (bottom of `js/app.js`) exposes `readProfile()` and
  `lastRun()` read-only, purely so a driver can tie a rendered number back
  to the engine instead of comparing the DOM against itself. Nothing in the
  app consumes it.

## What is NOT modeled (keep this list current)

Disclosed to the advisor in the results-panel fine print and (where noted)
flagged dynamically when it actually applies — update BOTH this list and
the fine print together if you close one of these gaps:

- **AMT** — not computed at all.
- **Depreciation recapture on sale** — not modeled in general. The 6
  accelerated-depreciation strategies (bonus depreciation, §179, cost
  segregation, QIP bonus, §179D, heavy vehicle §179) each track their
  claimed acceleration into `state.acceleratedDepAccumulated`, and
  `scenario-engine.js` raises a quantified note if the cumulative total
  crosses a materiality threshold — but no actual recapture tax is ever
  computed, even at a modeled disposition (there is no disposition/sale
  event in this tool at all).
- **Rental income never enters the §199A QBI calculation** — real rental
  activity CAN generate QBI (rising to a §162 trade/business, or via the
  Rev. Proc. 2019-38 safe harbor), but `qbiDeduction()` in `tax-engine.js`
  intentionally excludes `rentalNet` from `qbiIncome`.
- **QBI's 25%-of-wages + 2.5%-of-UBIA alternative limitation is absent** —
  only the 50%-of-wages prong is modeled (`entityW2Wages` × 50%); a client
  with substantial qualified property and modest wages is understated.
- **Projection years 2+ apply 2026 DOLLAR THRESHOLDS to every year shown,
  never inflation-indexed forward** — enacted sunset dates ARE modeled
  (`projTaxYear`, threaded per year by `scenario-engine.js`: e.g. the OBBBA
  senior deduction expires after 2028, the enhanced SALT cap reverts to a
  flat $10k/$5k after 2029 — see `saltCapForYear()` in `tax-engine.js`), but
  every bracket, threshold, and breakpoint stays at its 2026 dollar figure
  for the whole projection — a multi-year projection is not literally "what
  the return will say" in year 5 or 10, since real brackets would have
  drifted with inflation by then. Indexing would require guessing a future
  CPI assumption, so this is a deliberate simplification, disclosed in the
  fine print and the client PDF's outlook-page disclaimer.
- **State tax** — flat effective rate the advisor enters; no state-specific
  bracket/credit modeling. An optional entity-level state rate can be
  layered on top for the C-corp/S-corp strategies (`corpStateRatePct` /
  `entityStateTaxPct`), and QSBS has a nonconforming-state add-back
  (`stateIncomeAddBack`) — both are flat-rate starting-point estimates, not
  apportioned multi-state computations.
- **Medicare IRMAA surcharges** — flagged as a quantified NOTE only
  (`scenario-engine.js`, gated on `age65Count > 0`) when a projection year's
  MAGI crosses a 2026 CMS tier; the surcharge itself is never added to any
  total — it's a Medicare premium impact, not a tax.

If the calendar year moves past `TSIQ.TABLES_2026.taxYear`, `app.js`'s
`checkLawStaleness()` shows a persistent banner and appends a warning to
the fine print / client PDF disclaimer — that is a symptom of these tables
needing a refresh for the new year, not a separate bug.

## Working conventions

- Every renderer/`app.js` function that builds HTML from client- or
  advisor-entered text must escape it with `TSIQ.esc` (defined in
  `tax-tables-2026.js`) — this app renders client names, firm names, and
  notes directly into `document.write()`'d popup windows.
- A strategy's `apply(profile, params, yearIndex, state)` must never
  mutate `profile` in place — `var p = Object.assign({}, profile);` first,
  return `{ profile: p, notes: [...] }`. Push user-facing notes only on
  `yearIndex === 0` unless the note is genuinely year-specific.
- Multi-year cross-strategy coordination goes through the shared `state`
  object (e.g. `state.hasQualifiedPlan`, `state.dcAnnualAdditionsUsed`,
  `state.acceleratedDepAccumulated`) — namespace your keys.
